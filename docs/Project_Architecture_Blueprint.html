Node.js、TypeScript、pnpm workspace、Fastify、Zod、DeepSeek，以及目标态的 Taro + React。

当前架构模式

Layered monorepo + single business API + internal worker + shared package boundaries。

H5 bootstrap 已经成型

当前真正跑起来的是 H5 Fastify shell + API + worker，而不是最终双端 Taro client。

Target Truth

目标是共享业务前端

目标态是一套 Taro + React 代码编译到 h5 和 weapp，平台差异只放进 adapters。

Core Invariant

persona_version 是公开单元

publish、review、share、preview、chat 全部围绕不可变版本展开，而不是围绕裸 persona。

03

核心架构组件

这里按蓝图视角说明每个核心组件的职责、边界和演进方向。

apps/client

当前是 H5 Fastify shell，负责页面壳、内联脚本和请求承接；目标是共享的 Taro 双 target client，且用户端不再承接 reviewer 工作台。

  • 当前实现边界：H5 页面路由、布局、请求触发。
  • 目标边界：pages / features / services / adapters。
  • 关键要求：平台差异放进 adapters，不扩散到业务层。

apps/api

统一业务 API，是 publish、share、chat 和 persona lifecycle 的真相持有者；review 只保留为后续 admin 项目的后端能力。

  • route 负责输入输出边界。
  • store / workflow 负责业务编排。
  • worker 只是计算依赖，不是业务状态拥有者。

apps/worker

负责 source-ingest 和 distill 这两类 pipeline-like 任务，当前通过 internal HTTP 被 API 调用。

  • 当前：internal HTTP service。
  • 目标：queue-backed worker。
  • 不应在 worker 内持有业务真相。

Shared Packages

整个项目最重要的架构稳定器是 shared packages，而不是某一个 runtime app。

  • contracts：传输边界
  • domain：状态机和业务词汇
  • prompt-kit：prompt 和 output schema
  • deepseek-client：模型 provider 适配

05

横切关注点

这些内容决定架构是否稳定，而不是只是决定某个页面是否能跑。

认证与鉴权

  • 角色：ANONYMOUS / USER / REVIEWER
  • 平台登录入口不同，业务会话体系统一。
  • reviewer-only route 在业务后端保护，reviewer UI 后续放到独立 admin 项目。

验证与边界

  • transport validation 在 packages/contracts
  • LLM output validation 在 packages/prompt-kit
  • business vocabulary 在 packages/domain

弹性与回退

  • DeepSeek 失败时有 deterministic fallback。
  • chat 和 feedback 有 rate limit。
  • URL ingest 有 guardrails，但还不是最终生产级抓取链路。

服务通信模式

  • client -> API：同步 JSON
  • API -> worker：当前 internal HTTP
  • API/worker -> DeepSeek：structured JSON request
  • 目标：ingest/distill 迁移到 queue-backed worker

06

治理、扩展与新开发蓝图

后续扩展应该遵循固定的放置规则，否则很快会把 monorepo 的边界打穿。

新增功能的安全顺序

  • 先锁 contract，再锁 domain invariant。
  • 再决定放在 API 同步链路还是 worker 异步链路。
  • 新 prompt 和 schema 放进 prompt-kit。
  • provider 访问只放进 deepseek-client。

后续主要迁移方向

  • store 从 in-memory 迁到 PostgreSQL-backed repositories。
  • worker 从 internal HTTP 迁到 queue-backed execution。
  • H5 shell 向共享 Taro client 收敛。
  • source ingest 从 placeholder snapshot 升级到真实内容提纯。

07

最终架构判断

这部分是给后续实现窗口和评审窗口直接复用的总结。

Hall of Fame 的正确架构解释是：今天它是一个 layered Node.js monorepo，带有 H5 bootstrap、unified API、internal worker、strong shared package boundaries 和 transitional persistence；目标它是一套 shared Taro dual-target client、PostgreSQL-backed business truth、queue-backed worker execution，以及 version-first persona publishing model。这个“双真相模型”不是文档噪音，而是这个项目最核心的架构现实；对应的产品边界也已经收紧为用户端只保留 聊天 / 创建 / 我的，review 工作台后续独立到 admin 项目。
